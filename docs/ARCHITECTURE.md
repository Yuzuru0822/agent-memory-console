# 架构与扩展

工程将界面、受限桌面接口和本地服务分开。React 只展示数据及发起固定操作；文件访问、授权检查、备份、子进程、积分领取及余额监控均位于 Electron 主进程。v0.3.0 引入 Windows UI Automation，v0.4.0 扩展领取后自动执行与独立余额监控；原生桥接仍只接收固定 JSON 请求。

## 状态与发现

适配器列出候选记忆文件、技能目录及 EXE。用户绑定优先于候选路径；未绑定时选择第一个存在的候选，没有候选存在则显示第一个待发现路径。候选扫描只读，不执行程序、不注册服务，也不构成同步授权。

Qoder 使用 `mode: 'desktop'`，提供国际版 `~/.qoder/skills` 和 CLI 静态指令 `~/.qoder/AGENTS.md` 候选；后者不代表 IDE 自动记忆。IDE EXE 候选覆盖新旧名称、常见安装目录及最多 128 个 PATH 目录，路径末尾为 `bin` 时也检查父目录；不解析脚本、不读取注册表。项目文件、地区版和自定义目录交由用户明确绑定，未实现 Qoder CLI 任务协议。

Claude adapter 另携带 npm 发现选项。`createAdapters` 默认使用空环境以隔离单元测试；生产主进程显式传入环境。`approveNpm` 在原生确认后保存 `claudeNpm` 描述（locator、包元数据路径、版本、实际入口、需要时的 Node）；它与原生 EXE 配置互斥。撤销程序授权同时清除该描述。主进程 `Processes.validate` 在每次启动前解析并比较描述，`launch` 使用实际 EXE + 固定参数数组，永不执行 CMD。既有 version 1 配置兼容这个新增可选字段，无需迁移记忆路径或备份。

`ready` 表示记忆和技能路径存在且检查通过，`partial` 表示至少发现一个路径或程序，`missing` 表示均未发现，`attention` 表示读取或安全检查失败。进程状态单独保存，只来自本控制台本次运行创建的直接子进程。

记忆使用文件字节的 SHA-256 比较；字符数按 Unicode 码点统计。技能检查只遍历目录和文件元数据，不读取技能正文；统计实际路径去重后名为 `SKILL.md` 的文件数量，不验证技能语义或厂商加载结果。检查可以跟随本地目录及文件符号链接、junction，记录逻辑路径到实际路径的映射，检测重复目标、循环和断链。普通有效链接本身不构成 `attention`；检查最多遍历 20,000 个条目和 20 层，受限或异常时附带警告，不能把部分统计当作完整结果。

## 技能链接授权

技能目录保留用户选择的逻辑路径，Agent 配置新增可选 `skillsAccess`，共享源新增可选 `canonicalSkillsAccess`，保存确认时的实际根目录与链接映射。既有 version 1 配置无需迁移即可继续只读检查；含链接的旧路径需在“授权技能链接”中明确确认实际目标，才能同步或备份。新路径选择流程也使用原生确认框显示完整映射。记忆文件和普通程序路径仍走严格的非链接检查，npm 运行时使用独立的有限解析流程。

使用前重新解析逻辑路径并比较授权映射。链接改指其他位置、出现未授权链接或目标不再符合本地路径限制时，不沿用旧授权。显示链接映射也让用户看到对共享目标的写入会影响其他引用该目标的 Agent。

## 同步与恢复

### 统一仓库

v0.2.0 将仓库目录与旧版单一 Markdown 共享源分开。仓库包含 `memories/<agentId>/`、共享 `skills/`、`.git/` 与应用标识。中央仓库初始化仅接受空目录或已由本应用管理的仓库；其 Git 使用 `main` 分支，不接管任意第三方工作树，不接受外部对象存储或仓库内链接。技能内保留的独立 Git 仓库采用下述迁移规则，不受中央仓库的分支命名约束。控制台 Git 操作不启动 shell，也不执行 hooks。

纳管成员、记忆文件或目录、自动化设置保存在控制台配置。单文件记忆可沿用旧授权，多文件目录按相对路径映射到所属 Agent 分区，不把各厂商内容混成一份 Markdown。共同版本、同步备份及连接回执保存在控制台数据目录，不从 Git HEAD 猜测共同版本。

双向计划比较 Agent、仓库和上次成功同步的共同版本。单端修改沿用修改端；两端不同位置修改尝试三方逐行合并；无共同版本且两端不同、同处文本冲突或二进制冲突必须由用户选择。手动编辑只用于文本。不会插入冲突标记，不会把缺失当作删除指令；一端独有内容补到另一端。

技能连接是独立的显式迁移。预览记录根入口身份、所有目录与文件证据、内容哈希及链接映射。导入完整字节后，将原技能入口改名保存为相邻备份，再创建指向仓库 `skills/` 的 junction。失效或循环项目跳过导入、保留原入口并提示；同名文件/目录冲突阻止迁移。发生失败时尝试撤回本次写入及入口变更；遇到并发改动则保留现场并给出恢复位置。

v0.2.1 允许显式迁移携带技能根目录及子目录中的普通 `.git` 目录，按完整元数据保留历史、refs 和远程配置，不对内层仓库提交、合并、运行 hooks 或访问远程。中央 Git 只索引技能工作文件，不收录内层 `.git`，也不将其转换成 gitlink。自动或手动双向复制忽略内层 `.git`；其共同版本只覆盖工作文件，不推断或合并内层提交图。中央仓库的提交不能替代内层 Git 元数据备份。

内层仓库必须完整独立：外置 `.git` 文件、共享 worktree、`alternates` 对象库等对外依赖会阻止迁移，应先准备不依赖原位置的独立 clone。迁移保留的原入口包含原 Git 元数据；连接后 Agent 路径与仓库路径访问同一份内层 Git，用户在任一路径进行的 Git 操作会作用于同一仓库。

`git-migration.ts` 校验 `HEAD/objects/refs` 结构、配置格式与外部依赖；迁移枚举另拒绝 Git 元数据内链接及锁文件。每个内层 `.git` 生成覆盖完整目录、文件内容与大小的指纹；目标同名仓库仅在指纹相同时复用，指纹不同在写入前整仓库拒绝，不使用普通文件冲突选择器合并历史。导入后再次核对元数据指纹。普通文件限制 32 MiB，Git pack 文件限制 128 MiB，迁移总体仍限制 5,000 个文件、256 MiB。

解除连接仅移除仍指向同一仓库的已核验 junction，再将原入口改名恢复；不会递归删除仓库。已连接 Agent 对技能的编辑直接作用于共享文件，不需要重复复制。自动同步是应用生命周期内的定时检查，不是 Windows 服务；首次启用和修改策略经过原生确认，冲突留待人工处理。

### 兼容模式

1. 共享源和目标通过原生路径选择器绑定；技能链接的实际目标另经明确确认。目标写入权限只来自持久化的明确绑定和当前有效的链接映射。
2. `preview()` 生成逐文件计划：逻辑来源与目标、解析后的实际来源与目标、旧/新内容、哈希和大小。技能路径按来源相对目录映射，实际目标用于重叠与重复检查。
3. 计划仅存于内存，有效期五分钟。创建新计划会替换旧计划；保存路径配置会清空计划。
4. 用户检查预览并确认后，主进程再次显示实际目标列表。
5. `apply()` 检查计划、授权配置、全部链接映射、源/目标哈希和活动链，先备份全部现有目标，再逐文件重新解析并检查后写入。
6. 每个文件在实际目标同目录创建临时文件，写入、刷新后重命名替换，并校验结果、记录日志。源链接内容作为普通文本复制，目标已有符号链接和 junction 保持原状；不复制链接对象。

文本同步仍限制单文件 1 MiB、单次最多 200 个文件和 16 MiB、目录最多 20 层，与只读技能统计的容量限制分开。多文件操作不是事务。若中途失败，已完成的文件会保留，现有目标可通过自动快照恢复；新增文件不会因恢复而删除。

快照保存实际目标及原始 `logicalTarget`。恢复读取快照清单、检查备份内容哈希，并使用当前授权重新解析逻辑目标，再走相同的预览和写入流程。撤销、更换授权或链接改指后，旧快照不能绕过当前授权写入旧位置。

## 积分福利与余额监控

v0.3.0 的奖励适配器与七个 Agent 的文件/启动适配器相互独立：九个平台条目中，Qoder 国际版、Qoder CN、TRAE CN 和 WorkBuddy 提供可校准 UI 流程；千问办公、智谱 ZCode、Claude Code、TRAE 国际版和 DeepSeek Harness 仅展示自动发放、需人工处理或尚未接入的说明。增加文件适配器不会自动获得领取权限。活动规则与证据见 [积分活动说明](REWARDS.md)。

用户通过原生文件选择和确认绑定领取客户端，保存 EXE 路径与 SHA-256；既有启动授权不沿用。每次流程重新校验文件摘要，客户端升级后要求重新绑定。用户自行登录并打开窗口；服务不管理登录、不读取凭据，也不自动识别切换后的账号。地区配置独立，平台和时间窗口去重不能替代账号身份校验。

`inspect` 生成短期观察令牌，供 UI 从实际返回的控件中选择。记录导航会立即调用该控件；记录领取控件只保存配置。领取配置还需要窗口标题、活动上下文、明确成功文案和每日重置时间。校准和执行占用操作锁，观察过期、程序或配置变化后需重新检查。`RewardsService.start()` 先调用 `run()` 试领，只有流程已验证且结果为 claimed / already_claimed 才调用 `automation(true)`；首次仅看到“已领取”不会将流程标记为已验证。UI 的“验证并开启自动领取”将本次试领和成功后的自动执行合在一次原生确认中。

运行时重新检查窗口，按保存的导航到达活动页，确认上下文和唯一领取控件。提交前先持久化“未知”标记，再调用桥接；桥接在同一目标窗口内重新检查上下文后才执行。提交后重复检查明确结果；超时、上下文丢失或无法确认成功时保留未知并暂停自动执行，重启也不自动重试。跨日切的提交按实际领取窗口记录；提交和成功核验跨越窗口时保持未知，避免错误去重。用户需先核对客户端结果，再重新校准。

主进程生命周期定时器串行检查统一仓库、积分领取与余额任务；积分服务每轮至多处理一个平台，依据其 UTC+8 领取窗口判断是否到期。余额服务轮转处理到期平台，避免同一条目长期占据检查机会。自动流程默认关闭，开启需成功校准和原生确认。领取或余额校准期间暂停后台 UI 调度，避免页面被其他任务切换。锁屏等提交前失败只推迟后续检查；已经提交后的未知结果关闭自动并要求人工核对。它不是 Windows 后台服务，关闭控制台即停止调度。

Node 只启动固定路径的 `RewardBridge.exe`，通过 stdin/stdout 传输单个 JSON 请求/响应，不传代码、脚本或命令。开发路径为 `native/bin/RewardBridge.exe`，打包路径为 `resources/rewards/RewardBridge.exe`。桥接只支持 `inspect` 与 `invoke`：精确核验 EXE、可见且非最小化的唯一顶级窗口，在该窗口内遍历控件；调用前复核桌面、进程、窗口身份、唯一 selector 与活动文本。详细限制见 [安全边界](SECURITY.md)。

`RewardsBalanceService` 为全部九个平台提供独立的手动校准入口，与领取类别和授权分离。每个平台只保存一个用户选定的余额字段，记录单位、5–1440 分钟间隔（默认 15）和可选非负阈值。它没有厂商余额 API、凭据读取或账号发现能力；真实客户端必须提供可识别的余额 Text 控件。重新绑定、重新配置或重置会清除该平台旧历史，避免混合账号和字段。

余额识别支持包含标签与数字的单个 Text，或同一小容器中的两个直接同级 Text。原生桥接使用 `RawViewWalker`，只在实际直接父节点也输出时附带 `parentIndex`；隐藏或遗漏父节点断开关联，不沿祖先补齐。协议要求父索引已出现、小于当前索引且为整数，拒绝自引用、缺失、循环或未知字段。可见条目达到 500 个仍允许完整返回，出现第 501 个时整次观察失败，不截断树；隐藏条目不占此配额。分离文字还要求父容器不是 Window / Document 且直接子项至多 12 个。数值解析拒绝百分比、比例、日期、约数、缩写量级和多重匹配，找不到唯一明确值时不猜测。

余额导航仅允许已校准、唯一、启用且可见的查看控件；记录导航立即执行，后续读取从当前可见步骤继续。WorkBuddy 已核实的精确页面名“订阅和用量”是只读导航例外，购买、充值等子操作仍拒绝。余额页面含多个种类时只读取选定字段，不推算总余额或换算单位。

主进程向 `RewardsService` 注入余额观察回调。`before_claim` 只读取当前页，不能执行余额导航；领取服务随后重新检查活动窗口。`after_claim` 在提交后或观察到已领取后尝试读取，可按已保存导航到达余额页。该联动对已配置余额字段生效，不要求独立定时余额开关开启。余额失败在自身服务中保留旧值和错误，观察回调不会把已核验的领取变成可重试失败。

每次成功采样保存时间、值、单位、原因及与上次同单位采样的差值。零是有效值；缺失和读取失败不生成零值。失败或超过刷新间隔显示过期，旧值继续带原采样时间展示；低余额仅在数据新鲜、没有错误且不高于阈值时成立。差值可以包含消耗、到期或其他发放，不是领取收益，也不改变领取成功判定。

## 数据生命周期

配置、台账、共同版本及快照位于 `userData/console-data`。仓库记忆与技能的工作文件位于用户明确选择的独立目录。自动清理是可选设置，默认保留 30 天且至少 20 份仓库备份，仅清理受控备份与临时文件，不传播文件删除，也不清理技能迁移原目录或 Git 历史。兼容模式界面最多展示最近 100 份快照和 100 条活动。台账采用含序号、时间、上条哈希和本条哈希的 JSONL 记录；可检测部分意外损坏，没有外部签名或可信锚点。

`rewards.json` 保存独立的积分配置、选择的窗口和控件文案、领取窗口状态及结果日志；读取上限 2 MiB，结果日志保留最近 200 条、界面显示最近 100 条。积分授权、自动化与结果事件另写入现有活动台账。配置为本机明文，不保存登录令牌；选定的可见文案仍可能含个人信息。领取状态不是厂商签名收据，也不能证明实际余额。

`balances.json` 独立保存余额 EXE 摘要、窗口标题、导航、字段规则、单位、阈值、检查状态和每个平台最近 100 次成功采样，界面展示最近 20 次；文件上限 2 MiB。采样数值和状态也写入活动台账。余额历史和配置均为本机明文，不保存 API Key、密码或登录令牌；不跨平台合计数值。

同步计划、积分窗口观察、当前子进程对象与 CLI 输出只保留在内存。关闭应用时若仍有所属进程，会要求用户返回或放弃追踪；应用不会自动杀死这些进程。

## 添加适配器

当前扩展方式是编辑源码后重新构建，没有加载任意第三方插件代码的机制。

1. 在 `src/shared.ts` 的 `AgentId` 中增加 ID。
2. 在 `electron/adapters.ts` 注册名称、说明、外观、候选位置和能力。没有确认的厂商路径用空数组，无法验证的能力标为 `candidate`。
3. 通用桌面应用使用 `mode: 'desktop'`。目前 `mode: 'cli'` 专用于 Claude 的固定 `-p` 协议；新 CLI 必须先在主进程增加独立的参数与输入校验，不能直接复用此模式假定兼容。
4. 为新发现逻辑、输入限制和关键错误路径增加测试，更新集成文档。

适配器不得自行获得写权限、引入 shell 字符串、默认执行技能脚本或宣称未验证的厂商协议支持。需要新的登录、任务派发等能力时，应新增有明确输入类型和授权边界的主进程 API。

积分平台另在 `rewards-adapters.ts` 定义证据来源、活动分类与时间窗口。未确认可主动领取的权益应保持说明模式，不能把登录赠送、月度配额、兑换或付费操作改成领取按钮；新增 UI 流程也必须经过用户校准、成功试领及相关安全测试。

## 验证与交付

先运行 `npm run build` 和 `npm test`，再对构建产物运行 `npm run test:desktop`、`node tests/repository-desktop.cjs`、`node tests/rewards-desktop.cjs` 与 `node tests/rewards-balance-desktop.cjs`。积分与余额桌面测试使用真实 Electron/IPC/React 和模拟的 Windows 桥接，不调用真实客户端；原生协议和纯数据筛选测试也不等于实际领取或余额验证。真实客户端控件兼容性、账号资格、到账和余额仍需逐项校准，不能从模拟测试推断成功。

开发和生产构建都运行 `build:rewards`，使用系统 `%SystemRoot%\Microsoft.NET\Framework64\v4.0.30319\csc.exe` 及其 .NET Framework/WPF 引用；不下载编译器或执行 UIA。缺少系统组件时 Windows 构建失败，非 Windows 构建明确跳过桥接。完整要求见 [运行说明](../README.md)。

`npm run pack` 与 `npm run dist` 使用 electron-builder 输出 Windows x64 解包目录及 v0.4.0 便携 EXE；构建直接使用 `node_modules/electron/dist` 的已安装运行时，并将原生桥接复制到 `resources/rewards/`。解包成品使用 `node tests/packaged.cjs`，便携单文件使用 `node tests/portable.cjs` 验证启动。依赖由 `package-lock.json` 锁定，使用 `npm ci` 安装，Electron 当前固定为 `45.0.0`。写入测试使用隔离数据；覆盖、成品只读发现范围与结果见 [测试说明](TESTING.md)。真实账号的领取、到账与余额读取仍未验证。

开发模式提供 `CONSOLE_TEST_DATA` 和 `CONSOLE_TEST_HOME` 环境变量供测试隔离数据与用户目录；打包应用不接受这两项覆盖。请勿把测试变量配置在日常启动环境中。
